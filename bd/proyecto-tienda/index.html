Proyecto: base de datos de una tienda

  • ⏱ 90 minutos
  • 📶 Nivel: principiante
  • 🧩 Incluye ejercicio

💡 🎯 Al terminar esta lección podrás…

  • Diseñar un modelo de datos con varias tablas relacionadas.
  • Crear la base con un script reproducible y operarla con transacciones.
  • Escribir informes con JOIN, GROUP BY y HAVING.
  • Aplicar medidas básicas de seguridad y copias.

1.El encargo

Una pequeña tienda de tecnología de tu ciudad lleva sus ventas en un cuaderno y quiere pasarlas a una base de datos. Te pide poder:

  • Guardar el catálogo de productos con su categoría, precio y stock.
  • Registrar a sus clientes, sin repetir sus datos.
  • Anotar cada pedido con los productos y cantidades que incluye, y descontar el stock.
  • Obtener informes: cuánto vende, quién compra más, qué se vende más y qué no se mueve.
  • Estar protegida: datos coherentes, permisos limitados y copias de seguridad.

Es justo lo que has aprendido en las ocho lecciones. Aquí lo reúnes en un único proyecto, que funciona en SQLite (y con pocos cambios en PostgreSQL).

2.Paso 1: diseñar el modelo

Antes de escribir SQL, decide qué entidades hay y cómo se relacionan. Del encargo salen cuatro:

TablaQué guardaClave y restricciones
productosCatálogo: nombre, categoría, precio, stockid PK; NOT NULL en casi todo; stock DEFAULT 0
clientesNombre y correoid PK; email UNIQUE
pedidosUna compra: quién y cuándocliente_id FK a clientes
lineas_pedidoQué productos y cuántos hay en cada pedidoPK compuesta (pedido_id, producto_id); dos FK; CHECK (cantidad > 0)

Las relaciones son: un cliente tiene muchos pedidos (uno a muchos) y un pedido contiene muchos productos y un producto está en muchos pedidos (muchos a muchos, resuelto con lineas_pedido).

clientes 1a muchospedidos1 a muchoslineas_pedidomuchos a 1productos

💡 Consejo · Una decisión de diseño

El precio del producto está en productos, no en la línea del pedido. Pero entonces, si el precio cambia mañana, los informes de ventas pasadas cambiarían. En una tienda real guardarías también el precio vendido en lineas_pedido. Es un buen reto para el ejercicio.

3.Paso 2: crear la base de datos

Guarda todo en un único archivo tienda.sql. El script se puede ejecutar las veces que quieras: las líneas DROP TABLE IF EXISTS (en orden inverso a las dependencias) empiezan siempre desde cero. Este código se ha ejecutado de verdad en SQLite: crea 4 tablas con 8 productos, 4 clientes, 4 pedidos y 7 líneas.

tienda.sql
PRAGMA foreign_keys = ON;

DROP TABLE IF EXISTS lineas_pedido;
DROP TABLE IF EXISTS pedidos;
DROP TABLE IF EXISTS clientes;
DROP TABLE IF EXISTS productos;

CREATE TABLE productos (
  id        INTEGER PRIMARY KEY,
  nombre    TEXT    NOT NULL,
  categoria TEXT    NOT NULL,
  precio    NUMERIC NOT NULL,
  stock     INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE clientes (
  id     INTEGER PRIMARY KEY,
  nombre TEXT NOT NULL,
  email  TEXT NOT NULL UNIQUE
);

CREATE TABLE pedidos (
  id         INTEGER PRIMARY KEY,
  cliente_id INTEGER NOT NULL REFERENCES clientes(id),
  fecha      TEXT    NOT NULL
);

CREATE TABLE lineas_pedido (
  pedido_id   INTEGER NOT NULL REFERENCES pedidos(id),
  producto_id INTEGER NOT NULL REFERENCES productos(id),
  cantidad    INTEGER NOT NULL CHECK (cantidad > 0),
  PRIMARY KEY (pedido_id, producto_id)
);

4.Paso 3: registrar un pedido con una transacción

Registrar un pedido toca varias tablas: crear el pedido, añadir sus líneas y descontar el stock. Si algo falla a medias, la tienda quedaría con datos incoherentes. Por eso se hace dentro de una transacción (lección 3): todo se guarda, o no se guarda nada.

Diego compra 1 Monitor FHD y 2 Ratones
BEGIN;

INSERT INTO pedidos (id, cliente_id, fecha)
VALUES (5, 4, '2026-10-06');

INSERT INTO lineas_pedido (pedido_id, producto_id, cantidad)
VALUES (5, 3, 1), (5, 2, 2);

UPDATE productos SET stock = stock - 1 WHERE id = 3;
UPDATE productos SET stock = stock - 2 WHERE id = 2;

COMMIT;

Si cualquiera de las instrucciones falla, ejecutas ROLLBACK; en lugar de COMMIT; y la base queda como estaba. Después de la transacción:

📌 Nota · PostgreSQL

Allí lo normal es no escribir el id: lo genera la base (columna identity) y lo recuperas con INSERT … RETURNING id para usarlo en las líneas. En SQLite también puedes usar last_insert_rowid().

5.Paso 4: los informes

Los informes son consultas que combinan todo lo aprendido: JOIN, GROUP BY, HAVING y LEFT JOIN … IS NULL. Los resultados que ves son los de la base original (sin el pedido nuevo del paso anterior).

Pedidos con cliente e importe

Pedidos con cliente e importe
SELECT p.id AS pedido, c.nombre, p.fecha,
       SUM(l.cantidad * pr.precio) AS total
FROM pedidos p
JOIN clientes c       ON c.id        = p.cliente_id
JOIN lineas_pedido l  ON l.pedido_id = p.id
JOIN productos pr     ON pr.id       = l.producto_id
GROUP BY p.id
ORDER BY p.id;

Gasto por cliente (incluye a quien no compró)

Gasto por cliente (incluye a quien no compró)
SELECT c.nombre,
       COUNT(DISTINCT p.id) AS pedidos,
       COALESCE(SUM(l.cantidad * pr.precio), 0) AS gasto
FROM clientes c
LEFT JOIN pedidos p       ON p.cliente_id = c.id
LEFT JOIN lineas_pedido l ON l.pedido_id  = p.id
LEFT JOIN productos pr    ON pr.id        = l.producto_id
GROUP BY c.id
ORDER BY gasto DESC;

⚠️ Importante · Fechas en PostgreSQL

El informe por mes usa substr(fecha, 1, 7) porque en el proyecto la fecha es texto AAAA-MM-DD. En PostgreSQL con una columna DATE usarías to_char(fecha, 'YYYY-MM') o date_trunc('month', fecha).

6.Paso 5: proteger la base

Un proyecto terminado no es solo el que consulta bien. Antes de darlo por cerrado revisa:

  • Integridad: PRAGMA foreign_keys = ON en cada conexión (SQLite) y NOT NULL, UNIQUE y CHECK donde correspondan.
  • Inyección: la aplicación solo usa consultas parametrizadas; ningún valor del usuario se pega en el SQL.
  • Permisos: la aplicación no usa la cuenta de administrador (rol con GRANT solo de lo necesario).
  • Datos personales: si añades usuarios con contraseña, guarda solo el hash (bcrypt o Argon2).
  • Copias: un comando de respaldo programado y una restauración probada.

8.Errores frecuentes


  • Empezar a escribir tablas sin diseñar antes las entidades y relaciones: luego hay que rehacer todo.
  • Olvidar PRAGMA foreign_keys = ON al cargar el script y al conectar desde la aplicación.
  • Cargar datos antes de crear las tablas relacionadas, o crear las tablas en orden incorrecto: primero las que no dependen de otras.
  • Registrar un pedido sin transacción: un fallo deja el pedido sin líneas o el stock sin descontar.
  • Informes con INNER JOIN que ocultan clientes o productos sin ventas: usa LEFT JOIN cuando haya que incluirlos.
  • Sumar importes tras un JOIN que repite filas (por ejemplo, unir pedidos con líneas y sumar un campo del pedido).
  • No guardar el script .sql y modificar la base a mano: no se puede reproducir.
  • No probar la restauración de la copia.





📒 Apuntes para llevar


  • Un proyecto de base de datos sigue cinco pasos: diseñar, crear, operar, informar y proteger.
  • Diseña primero: entidades, relaciones (uno a muchos, muchos a muchos), claves y restricciones.
  • Guarda el esquema y los datos en un script .sql que se pueda ejecutar de nuevo; es la documentación de tu diseño.
  • Las operaciones que tocan varias tablas van en una transacción: BEGIN; … COMMIT; o ROLLBACK;.
  • Los informes combinan JOIN, GROUP BY, HAVING y LEFT JOIN … IS NULL.
  • Protege: claves foráneas activas, consultas parametrizadas, rol con pocos permisos, hash de contraseñas y copias probadas.
  • Con pocos cambios (identificadores, fechas, ILIKE) el mismo proyecto funciona en PostgreSQL.





9.Glosario




TérminoSignificado


Modelo de datosDescripción de las tablas, sus columnas y las relaciones entre ellas.
EsquemaConjunto de definiciones de las tablas y restricciones de una base de datos.
Script SQLArchivo .sql con instrucciones que se pueden ejecutar para reconstruir la base.
TransacciónGrupo de operaciones que se aplican todas o ninguna.
InformeConsulta que resume datos para tomar decisiones (ventas, stock, clientes…).
Ticket promedioImporte medio de cada pedido.
Datos huérfanosFilas que apuntan a otra fila que ya no existe; las claves foráneas lo evitan.
RespaldoCopia de seguridad de la base que permite restaurarla tras un fallo.
