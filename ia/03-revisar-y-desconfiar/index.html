Revisar, probar y desconfiar: seguridad con código de IA

  • ⏱ 55 minutos
  • 📶 Nivel: intermedio
  • 🧩 Incluye ejercicio

💡 🎯 Al terminar esta lección podrás…

  • Revisar un diff con una lista de comprobación antes de aceptarlo.
  • Detectar paquetes y funciones inventadas, y secretos mal manejados.
  • Escribir una prueba rápida con el ejecutor de pruebas de Node.

El código de IA suele verse perfecto: ordenado, con comentarios y nombres claros. Eso es parte del problema, porque baja tu guardia. Tu trabajo pasa de "escribir" a revisar, y revisar bien es una habilidad que se entrena.

1.Lista de revisión del diff

  1. ¿Pedí esto? Que no haya cambios en archivos que no mencionaste ni "mejoras" no pedidas.
  2. ¿Lo entiendo línea por línea? Si no, pídele que lo explique o simplifícalo. Código que no entiendes es deuda.
  3. ¿Existe todo lo que usa? Funciones, métodos y opciones: contrástalos con MDN o la documentación oficial.
  4. ¿Casos límite? Lista vacía, valor nulo, texto muy largo, usuario sin permiso.
  5. ¿Dependencias nuevas? Cada una es riesgo y mantenimiento. ¿De verdad hace falta?
  6. ¿Secretos o datos personales expuestos?

2.Paquetes inventados (slopsquatting)

Los modelos a veces recomiendan un paquete de npm que no existe. Los atacantes lo saben: registran esos nombres con código malicioso y esperan a que alguien ejecute npm install. Antes de instalar algo que la IA sugirió:

bash
npm view nombre-del-paquete          # ¿existe? ¿versión, fecha, autor?
npm view nombre-del-paquete time     # ¿cuándo se publicó? (muy reciente = sospecha)
# y revisa descargas semanales y el repositorio en npmjs.com / GitHub

💡 Consejo

Si el paquete tiene pocas descargas, se creó hace días o su nombre se parece a uno famoso con una letra distinta, no lo instales.

3.Los fallos de seguridad más comunes

  • Claves en el código (const API_KEY = "sk-..."). Van en variables de entorno y .env está en .gitignore. Si una clave se subió a GitHub, revócala y crea otra: borrarla del commit no basta.
  • SQL armado con texto ("... WHERE id=" + id): usa consultas parametrizadas (lo viste en el nivel de bases de datos).
  • Falta de validación en lo que llega del usuario, y falta de autorización ("¿este usuario puede borrar esto?").
  • CORS abierto a todo (*) con cookies o datos privados.
  • Contraseñas sin hash o con un hash débil.

4.Prueba lo que te dieron

Ejecutar el código una vez no es probarlo. Node trae un ejecutor de pruebas, sin instalar nada:

javascript
// total.test.js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { total } from './total.js';

test('suma precios', () => assert.equal(total([10, 5]), 15));
test('lista vacía da 0', () => assert.equal(total([]), 0));
test('ignora valores no numéricos', () => assert.equal(total([10, 'x']), 10));
bash
node --test

Una buena práctica: escribe tú las pruebas (o al menos revísalas) antes de pedir el código. Así la IA tiene un objetivo verificable y tú un juez que no depende de ella. Si tu proyecto usa Vite, Vitest cumple el mismo papel.

5.Datos que nunca debes pegar

Lo que escribes en una herramienta de IA se envía a servidores de terceros. No pegues: claves y tokens, contraseñas, datos personales de clientes, código de tu empleador sin permiso. Si necesitas ayuda con un archivo de configuración, reemplaza los valores reales por marcadores (TU_CLAVE_AQUI). Revisa también las opciones de privacidad de cada herramienta (por ejemplo, si tus datos se usan para entrenar).

📒 Apuntes para llevar

  • Revisar un diff: ¿lo pedí?, ¿lo entiendo?, ¿existe?, ¿casos límite?, ¿dependencias?, ¿secretos?
  • Verifica cada paquete con npm view antes de instalarlo: pueden ser inventados o maliciosos.
  • Claves siempre en variables de entorno; si se filtran, revócalas.
  • Pruebas con node --test: mejor si tú defines qué debe pasar.
  • No pegues secretos ni datos de terceros en herramientas de IA.

6.Glosario

TérminoSignificado
SlopsquattingAtaque que registra nombres de paquetes que la IA suele inventar.
Consulta parametrizadaSQL que separa la orden de los datos para evitar inyección.
Caso límiteEntrada extrema o rara: vacía, nula, enorme, con símbolos.
Prueba automatizadaCódigo que comprueba que otro código hace lo esperado.
Revocar una claveInvalidarla en el proveedor y crear una nueva.
